# 实现补充约定

本文补充 Java DTO、数据库状态和异步任务之间的落地规则，不修改既有 OpenAPI。开发时应将新增的输入限制同步到 OpenAPI、App 表单和服务端校验。

## 1 内部状态到接口状态

| 存储位置 | 内部值 | API 对应值 |
|---|---|---|
| attachment.status | PENDING、VERIFYING | Attachment.status = WAITING |
| attachment.status | READY | Attachment.status = VERIFIED |
| attachment.status | FAILED | Attachment.status = REJECTED |
| offline_submission.status | RECEIVED | SubmissionReceipt.state = QUEUED |
| offline_submission.status | PROCESSING、APPLIED、CONFLICT、REJECTED | 同名 state |
| sync_exception.status | OPEN | SyncException.status = OPEN |
| sync_exception.status | RESOLVED | SyncException.status = RESOLVED |
| sync_exception 拒绝采用材料的处理结果 | resolution_json 保存拒绝动作及原因 | status 仍为 RESOLVED，不新增 API 状态 |
| service.phase | EDITABLE、FROZEN、AWAITING_CONFIRMATION、PUBLISHING、PUBLISHED | ServiceDraft.phase 同名 |
| facility.status | ACTIVE、INACTIVE、REMOVED | Facility.status 同名 |

通知已读、模块完成状态、逾期标记、是否可重试等由持久记录和业务规则派生，不使用客户端提交的展示状态作为业务事实。

## 2 有限列宽需要对齐的典型字段

以下建议以已提供 DDL 为准收紧模型；如果业务确实需要更长文本，应先扩展列宽，不能只在 Java 截断。JSON 内未单独索引的完整表单字段继续按 ServiceContent 约束保存。

| API 字段或含义 | 建议接口上限 | 对应物理字段 |
|---|---|---|
| 账号登录名 | 64 字符 | app_user.login_name |
| 员工名称与 signerName | 80 字符 | app_user.name、service_signature.signer_name |
| 客户和门店名称 | 160 字符 | customer.name、store.name |
| 客户、门店与设施编号 | 40 字符 | customer.code、store.code、facility.code |
| Store.address | 500 字符 | store.address |
| Facility.position、Risk.position | 300 字符 | facility.position、risk.position |
| floor | 40 字符 | facility.floor、store_area.floor |
| 责任方描述 | 100 字符 | risk.responsible_party |
| 独立原因字段 | 1000 字符 | task_change.reason、confirmation_exception.reason 等 |
| deviceId | 128 字符 | auth_session.device_id、offline_context.device_id 等 |

其他 VARCHAR 字段逐一按《MySQL完整数据字典.md》生成 Bean Validation 约束，文本使用字符数限制、上传使用字节数限制。手机号规范化后单独限制，加密列按编码、认证标签和密钥版本预留容量，避免把明文字数直接当作密文字节上限。

## 3 签字替换和发布重试

签字替换与重开正文都锁 service 行。旧签字失效后，正在使用该凭证的 publication_job 变为 BLOCKED；对应 job_queue 的 fencing_token 增加，阻止仍在渲染的旧 Worker 发布。

如果正文不变且用户重新完成有效双签，再次调用 publications 时复用该 serviceId＋snapshotId 的 publication_job，在事务中更新本次指定的两条签字ID、重置队列状态并递增 token，同时追加审计。已失效 Worker 手中持有的旧 token 和旧签字均不能生效。不能只把 FAILED 改为 QUEUED 而沿用已经失效的签署凭证。

已成功发布的 snapshot 不允许替换报告内签字；此类修改必须创建新正文版本并重新双签。重试只影响未成功的尝试，不改变已经发布的报告对象。

## 4 风险事件和投影规则

NO_CHANGE、NOT_CHECKED 也是新的跟进事实：追加 ledger_event 和 risk_followup，风险 revision 递增，但不改变整改状态。新风险 revision 从 1 开始；重复事件命中原回执而不再次递增。

Capture 没有独立UUID，snapshot_finding.source_record_id 使用 Inspection.id，唯一键为 snapshotId＋source＋sourceRecordId＋pestTypeId。客户反馈与现场发现使用 Finding.id。每次设施检查同一虫种只能出现一条捕获记录；服务端发现重复时返回 422，不默默合计。

snapshot_* 记录和正文快照在同一事务生成。投影版本升级应通过受控迁移或重建影子事实后校验，不允许在普通 API 中修改已冻结的事实。风险快照、药剂名称用量和静态评估仍取正文及上下文，不取实时台账补值。

## 5 待实现的校验边界

SQL 只约束列、部分状态、外键和唯一性。登录安全、数据范围、风险状态转换、完整性 V01—V16、签字角色与快照一致性、附件真实内容与摘要、离线授权、租约最终提交以及 PDF 文件检查，必须由 Java 和安卓实现并进行独立验收。配套的 19 项数据库检查不代表这些应用能力已经完成。
