# 领域术语与架构决策

## 领域术语

| 术语 | 业务定义 | 边界 |
|---|---|---|
| 客户 | 与虫控公司存在服务关系的主体 | 可管理多个品牌和门店 |
| 门店 | 实际开展虫害服务的场所 | 授权、设施、风险和历史服务的归属 |
| 服务任务 | 一次计划执行要求 | 有日期和主执行人，可以改派或取消 |
| 实际服务 | 一次现场作业 | 可以产生更正版报告，仍是同一次服务 |
| 设施 | 持续存在的防治或监测点位 | 与每一次检查记录分开 |
| 虫情 | 客户反馈、现场发现或设施捕获的原始观察 | 必须保留来源，数量可以不明 |
| 风险 | 需要整改的结构、卫生或管理问题 | 跨多次服务延续，不随服务结束关闭 |
| 处置 | 对虫情、设施问题或风险采取的行动 | 可以清洁、封堵、调整设施，不必使用药剂 |
| 报告正文 | 双方确认的当次服务内容 | 签字后不能继续修改并沿用原签字 |
| 正式报告 | 系统校验和生成成功后的完整确认结果 | 已发布版本可追溯，更正需重新确认 |

## ADR 001 首期采用模块化单体和独立 Worker

状态：Proposed。日期：2026-11-11。

一家公司的首期服务闭环涉及草稿、台账、快照和签字的原子应用，因此选择单库、模块化 Java 业务代码和本地事务。PDF 与批量任务独立进程运行，使用持久任务队列。代价是模块共享数据库、数据库升级和版本发布需要协调；换来较少的分布式故障状态。暂不采用按业务模块划分微服务；当明确出现独立团队发布和不可通过单模块扩容解决的负载后再评估拆分。

## ADR 002 正文采用固定规范字节并建立查询事实

状态：Proposed。日期：2026-11-11。

离线签署和长期历史报告要求正文不受门店台账、字典和 JSON 再序列化影响，因此保存固定上下文、JCS 正文字节和独立签署凭证；常用查询另存关系事实。代价是存储重复和投影校验工作；换来可重复验算的摘要与稳定报告。事实表只能从快照生成，同事务写入，不作为独立编辑对象。

## ADR 003 首期用 MySQL 持久队列承接后台工作

状态：Proposed。日期：2026-11-11。

为使业务写入与任务登记一次提交，首期把事务发件箱和内部执行队列合并为 job_queue。任务至少执行一次，通过业务唯一键、租约及 fencing_token 实现只生效一次。代价是队列和在线业务共用数据库资源；需小批量领取、限制并发和监控积压。未来接入消息队列时保留数据库发件箱与消费去重，不修改报告业务唯一性规则。
